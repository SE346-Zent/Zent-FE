# Scheduling & Time

This section details the platform's chronological mechanics, including complex time-window assignment algorithms, localized temporal conversions, and duration flag systems engineered for macro-oversight.

### 22. Does the system manage appointment scheduling/time slots, or just assignment?

**Response:**
To execute field operations successfully without destroying Customer Satisfaction Score (CSAT) margins, a platform cannot blindly dispatch technicians without predefined chronological bounds. 

The Zent platform must inherently support aggressive **Time Slot Window Management**. When a Work Order is routed into the unassigned queue via the upstream OEM integration, that JSON payload typically contains a tightly defined appointment metric structured during the initial customer telephone triage (e.g., *Requested Service Window: Monday, November 12th, 09:00 AM - 13:00 PM*). 

The Central Dispatch Administrator’s Dashboard algorithmically cross-references this static time window against the visual map. The Administrator performs the physical technician assignment strictly within the logical confines of these temporal blocks. When the selected Technician boots their mobile UI daily agenda, the system sorts and prioritizes their assigned daily manifest implicitly relying upon these distinct appointment block variables, structuring an optimized and predictable driving route sequence.

### 23. Is there an ETA feature for customers to know when the technician will arrive?

**Response:**
Yes, deploying an automated ETA vector is the single most effective technological mitigation against the high financial overhead induced by "Customer Not Available / Door Locked" failure scenarios. 

This mechanism is deeply intertwined with explicit Technician procedural triggers. When the Technician presses the crucial "Start Trip" or "En Route" UI hook indicating they have concluded their previous engagement and have physically mobilized toward the next target, the backend immediately intercepts the current geolocation payload. It pipes this raw vector alongside the destination matrix into the Google Maps Distance Matrix API calculation engine. 

The resulting mathematically projected delay is subsequently embedded within a localized SMS gateway payload distributed instantly to the registered customer: *"Your Zent certified Technician has departed and is estimated to arrive in approximately 34 minutes. Please ensure someone over 18 is present to authorize access."* 

### 24. Does the system enforce working hours? Can a technician start a service at 11 PM?

**Response:**
Software should not structurally prohibit operations that physical management has authorized, especially concerning catastrophic enterprise hardware interventions. 

If a primary data center suffers a terrifying structural fault wiping out a foundational server rack, a certified Technician may absolutely be deployed at 23:45 PM to perform emergency swap mitigation until morning. A simplistic application logic that forcefully locks users out of Check-in functions because the server clock reads outside 9-to-5 "business hours" will induce catastrophic service failures.

The application architecture deliberately remains temporally agnostic concerning explicit check-in bounds. The Technician is mathematically capable of executing a service session entirely at 3:00 AM. In subsequent iterations of the dashboard reporting analytics, late-night triggers can be mathematically flagged visually as anomalous data points allowing Operations Management to perform payroll auditing, ensuring overtime thresholds are logged, but the raw execution of the physical repair sequence is never artificially blockaded.

### 25. How are timezones handled? What if Company X operates across timezone boundaries?

**Response:**
Chronological fragmentation across international and interstate lines is guaranteed to collapse database sorting integrity unless rigorous universal baseline standardization is enforced relentlessly.

The absolute, unyielding standard across the entire Zent structural stack demands that every single temporal timestamp generated by any client device, injected via API, or recorded in any audit trail is strictly captured, transmitted, stored, and calculated purely in the **UTC-0 (Coordinated Universal Time)** format. 

The mobile application running atop the hardware effectively acts as a localized translation engine. When it pulls an array of Scheduled Appointment strings down from the cloud API (stored entirely in UTC), the device's inherent localization libraries parse that data structure against the exact regional clock setting natively operating the tablet at that specific physical location. This ensures absolute historical accuracy irrespective of whether the Technician crosses state lines modifying their localized device clock halfway through an active afternoon shift.

### 26. Is there a maximum allowed duration for a service visit? Does the system flag overly long visits?

**Response:**
Yes. A maximum expected duration threshold acts as an omnipresent health tracker for the fleet efficiency metrics. 

While the system does not forcibly eject a Technician from an active session, an automated background Chron sweep monitors all entities marked `IN PROGRESS`. While most standard localized diagnostic repairs should conclude well within a two-to-three-hour window, the system typically sets a generous critical failure threshold at **6 consecutive hours**.

If a single intervention extends past this 6-hour checkpoint without exhibiting state progression, a glaring visual anomaly warning is pinned permanently against that specific active row on the centralized Dispatcher HUD. A protracted Work Order may imply highly adverse technical complications, aggressive customer disputes halting action, or simply a Technician experiencing a medical emergency on-site. Flagging these duration breaches empowers the Dispatcher to manually dial the Technician via cellular network to intercede and ascertain operational viability before deploying emergency secondary countermeasures.
